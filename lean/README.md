# Lean formalization: the specialization has group Sz(8)

This directory is a Lean 4 project. Lean's kernel checks that the Galois group of the degree-65 specialization
`f(X, -7/5)` over `ℚ` is isomorphic to Suzuki's group `Sz(8)`:

```lean
theorem Sz8.Galois.gal_specialization_equiv_suzuki :
    Nonempty (paperSpecialization.Gal ≃* Suzuki.Suzuki Suzuki.θ8)
```

## What the statement means

* `Sz8.Monodromy.paperSpecialization : ℚ[X]` is `f(X, -7/5)`, built from the exact coefficients of `data/f.json`.
  They are exported to `Sz8/Monodromy/Inputs.lean` by `export_inputs.py`.
* `Suzuki.Suzuki θ8` is Suzuki's definition of `Sz(8)`: the subgroup of `SL₄(𝔽₈)` generated by the matrices
  `T(a, b)`, `M(κ)` and `W` (`Sz8/Galois/Suzuki.lean`), with `θ8 x = x⁴`. `𝔽₈ = 𝔽₂[z]/(z³ + z + 1)` is a
  computable field whose ring and field axioms are kernel checks over all elements. No classification of
  finite simple groups is used, and nothing asserts that this group is characterized by its order.

Along the way:
* `Sz8.Galois.generic_galois`: over `ℚ(t)`, the Galois group of `f` acting on its 65 roots is the explicit
  permutation group `G = ⟨σ₁, σ₂⟩` of order 87360. `σ₁` and `σ₂` are the recorded meridian permutations of
  `data/monodromy.json`, identified with Mathlib's covering-space monodromy of certified loops.
* `Sz8.Galois.gal_specialization_eq_N` and `card_gal_specialization`: the specialization's Galois group is
  `N = [G, G]`, of order 29120.
* `Sz8.Galois.N_equiv_suzuki`: `N ≅ Sz(8)`, through the action of Suzuki's group on its 65-point ovoid.

The regular realization over `ℚ(s)` by the cubic base change is not formalized.

## Trust

Every audited declaration uses at most the axioms `propext`, `Classical.choice` and `Quot.sound`. No
`native_decide` and no `sorry` appear anywhere. Computations are replayed by `decide +kernel` on the kernel's
arbitrary-precision arithmetic. `verify.py` performs the following checks:
* builds `Sz8.Monodromy` and `Sz8.Galois` and fails if any declaration uses `sorry`;
* prints the axioms of every audited declaration (`Audit.lean`) and compares the list;
* requires twenty negative tests, in which the checkers reject corrupted certificates.

External programs only propose data. PARI/GP and python-flint produce root enclosures, residue witnesses and
Bézout certificates; GAP produces the ovoid relabelling; a numerical continuation plan (`certs/meridian1.json`)
supplies the Rouché steps. Lean checks everything it uses.

## Reproduce

Requirements:
* Python 3.11 with `sympy` and `python-flint` (see `../requirements.txt`) and PARI/GP;
* Lean through [elan](https://github.com/leanprover/elan) (the version in `lean-toolchain`);
* memory: the build was tested with 32 GB; the largest single process uses about 8 GB.

From the repository root:

```sh
make lean-data            # regenerate the generated Lean files and check them against their pinned hashes
cd lean
lake exe cache get        # prebuilt Mathlib for the pinned revision
sh tools/full_build.sh    # memory-heavy modules in small batches, then python3 verify.py
```

Do not run `lake update`: `lake-manifest.json` pins every dependency revision. `run-lake.sh` runs `lake`
here and prefers a compiler unpacked into `lean-4.34.0-rc2-darwin_aarch64/`. `make lean-verify` runs
`verify.py` once the project has been built.

Batch wall times are recorded on all platforms. Peak memory is recorded when macOS's `/usr/bin/time -l`
is available; otherwise the build runs without it and records `null` for `max_rss_bytes`.

On a 12-core Apple M2 Max with 32 GB, a build from an empty `.lake/build` took 48 minutes in batches, plus
19 minutes for `verify.py` (which builds the remaining modules). The largest single process used 8.3 GB. Mathlib
and the Hex dependencies were already compiled and are not included in these figures. `reproducibility.json`
records the original macOS rebuild from a copy of this repository. Its source hashes predate the later
build-script portability changes:
* hashes of every source file and of the pinned generated files;
* the input hashes, the compiler archive, tool versions and dependency revisions;
* per-batch time and memory, and the audit result for every declaration.

`tools/clean_rebuild.sh DEST` repeats it.

## Generated files

268 files are generated and not tracked by git (266 Lean files and two JSON reports; see `.gitignore`):
* the continuation certificates in `Sz8/Monodromy/Meridian/`;
* the input, group and normalizer certificates in `Sz8/Monodromy/`;
* the enclosure, invariant, node and Suzuki data in `Sz8/Galois/`.

`python3 tools/generate.py` (`make lean-data`) runs every exporter and checks the results against
`provenance/generated.json`. The exporters are `export_*.py`, and `galois/` holds the `Sz8.Galois`
generators and their recorded inputs (see `galois/README.md`). The exporters refuse to change a committed
provenance manifest (`provenance/export_*.json`), which records the generated bytes and the hashes of their
sources.

## Layout

| Path | Contents |
|---|---|
| `Sz8.lean` | The root module: imports `Sz8.Monodromy` and `Sz8.Galois` |
| `Sz8/Monodromy/` | Modular factorizations and Galois-order divisibility; the root covering and certified continuation steps; the two meridians; stabilizer-chain, Sylow and normalizer certificates for `G` and `N` |
| `Sz8/Galois/` | Seifert–van Kampen generation and puncture filling; the resultant identity and node analysis; the Galois–monodromy bridge; specialization into decomposition groups; the resolvent of a relative invariant with interval certificates; Suzuki's group and the isomorphism (`MainTheorem.lean` assembles the specialization theorem, `SuzukiGalois.lean` the final statement) |
| `Audit.lean`, `verify.py`, `test_*.py` | The axiom audit, its negative tests and the verification driver |
| `export_*.py`, `galois/`, `certs/`, `provenance/` | Exporters, generators, recorded inputs and provenance manifests |
| `tools/` | `generate.py`, batched builds, the snapshot/manifest writer and the clean-rebuild script |
